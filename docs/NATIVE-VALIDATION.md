# Native audit validation plan

This is a schedule by milestone, not a test result or a VM booking. The [audit](../AUDIT.md) retains **Not run** until observations exist. Do not retag or rebuild v0.3.0 to fill a row. For a new candidate, record the exact run ID and hashes, client build/revision, tested-on UTC date, operator, and redacted evidence. One run only establishes what it exercised.

## From plan to evidence

1. Pick one eligible [Windows candidate](WINDOWS-RELEASE.md#1-build-a-candidate-without-publishing) with passing CI and reserve both client VM configurations, including access to the mixed-DPI setup. Use the [working template](WINDOWS-RELEASE-EVIDENCE.md) for each OS/format. Don't schedule sign-off for a run whose artifact will expire before review.
2. Assign a tester and reviewer when the candidate is chosen. Add the actual scheduled date to the working record, then report **Pass**, **Fail**, **Blocked**, or **Not run** with observed UTC timestamps and durable redacted links. Keep failures and their re-test history.
3. Start automation with install/extract, real window launch/exit and a bounded fixture round trip on disposable Windows clients. Investigate native UI Automation and WebView2 instrumentation. Keep manual sign-off for unsupported cases, including Narrator or mixed-DPI until automation can verify them. Don't treat browser fixtures, Windows Server, or a standalone launch observer as full sign-off.
4. Only land [machine-checked candidate sign-off](release-evidence/README.md) when all required cases passed. Publish the matrix with the exact packages. Report driver, signing, fault and independent-review findings separately rather than filling missing rows by inference.
